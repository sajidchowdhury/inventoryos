    32→## 1. What InventoryOS Is
    33→
    34→InventoryOS is a SaaS-style, multi-tenant inventory management platform targeted at Bangladeshi retail pharmacies. A single Next.js 16 application serves **all tenants** — every business's data is isolated by `businessId` at the API and Prisma query level. The product is mobile-first (the primary end-user is a pharmacist behind a counter) with a desktop super-admin console at `/admin`.
    35→
    36→The long-term vision is to support **multiple business verticals** (pharmacy, grocery, restaurant, CCTV shop, mobile shop, electric shop, bakery) via a module registry (`src/lib/modules.ts`). Today only `pharmacy` is `isActive: true`; the other six are placeholders shown on the landing page as "coming soon". Adding a new vertical = adding an entry to `moduleRegistry` plus a `src/modules/<slug>/` folder mirroring the pharmacy layout.
    37→
    38→The product's differentiators vs. generic inventory tools are:
    39→1. **Batch + expiry tracking with FEFO** (First-Expiry-First-Out) dispensing engine — critical for pharmacies.
    40→2. **AI features** (shelf-scanner vision, expiry optimizer, smart forecast, smart reorder, AI chat, AI insights, product assistant) gated behind a paid `pro_ai` tier.
    41→3. **A 9-tier AI cost-control defense stack** so a single runaway pharmacy can't bankrupt the platform on LLM tokens.
    42→4. **Automated scheduled reports** that account for BD context: Eid (lunar, must confirm yearly), seasons (winter/summer/monsoon), and epidemic alerts (Dengue, COVID).
    43→5. **Super-admin ops console** at `/admin` for the founder to monitor AI spend, kill switches, cron health, and SMTP config.

   117→### 2.4 Conventions
   118→- **API route pattern**: every business-scoped route is under `/api/businesses/[id]/...`. The `[id]` is the `businessId`. The handler calls `requireBusinessUser(req, id)` (from `src/lib/auth.ts`) to verify the session belongs to a user of that business.
   119→- **All mutations write a `Transaction` row** for audit (type ∈ `PURCHASE | SALE | ADJUSTMENT | STOCK_IN | STOCK_OUT | WASTE | RETURN | QUARANTINE | RELEASE | DISPENSE | DISPOSE`).
   120→- **All AI calls** must go through `checkAILimit()` before the LLM and `logAIUsage()` after — see §6.
   121→- **No raw SQL** in routes. Use Prisma. The one exception is `src/lib/sql-router.ts` (super-admin only).
   122→- **Zustand stores** (`auth-store`, `nav-store`) hold client-only state. Server state is TanStack Query.
   123→- **Forms**: `react-hook-form` + `zodResolver` + zod schemas in `src/modules/<slug>/schema/`.

   240→## 5. Authentication & Multi-tenancy
   241→
   242→### 5.1 Onboarding flow (8 steps)
   243→`Landing → Phone → OTP → Discovery → Add Business → Create Login → Login → Dashboard`
   244→
   245→- Phone-first: `POST /api/auth/send-otp` (always returns success; OTP `9999` accepted in dev).
   246→- `POST /api/auth/verify-otp` → returns `phoneToken` + discovers existing businesses for that phone.
   247→- New user → `Add Business` step → `POST /api/businesses` (public) → `Create Login` → `POST /api/auth/register` (creates `BusinessUser` with role `owner`, sets username/password).
   248→- Returning user → picks a business → `POST /api/auth/login` → returns `session.token`.
   249→- `trusted-device` flow: owner can mark a device trusted → skips OTP on return.
   250→
   251→### 5.2 Middleware (`src/middleware.ts`)
   252→- **Edge runtime** — only checks token presence, never touches Prisma.
   253→- Token sources (priority): `Authorization: Bearer <token>` header → `session_token` cookie.
   254→- `PUBLIC_ROUTES` whitelist: `send-otp`, `verify-otp`, `register`, `login`, `super-admin/login`, `health`, `setup-status`, **and** `/api/businesses:GET` (only GET — mutations need auth).
   255→- For protected routes, the middleware forwards the token as `x-inventory-token` header so route handlers can read it consistently.
   256→- Route handlers then call `requireBusinessUser(req, businessId)` (Node runtime, Prisma available) for full verification + role resolution.
   257→
   258→### 5.3 RBAC (see `src/lib/rbac.ts`)
   259→6 roles with curated permission sets:
   260→- `owner` — full access including user management.
   261→- `admin` — same as owner except deleting other owners.
   262→- `manager` — inventory, sales, purchases, reports; no user management.
   263→- `pharmacist` — dispense + batches; no financial reports.
   264→- `cashier` — sales + payments only.
   265→- `stock_clerk` — stock + purchases; no sales.
   266→
   267→Permissions follow `<domain>.<action>` pattern (e.g. `batches.quarantine`, `reports.tax`). The client uses `usePermissions()` hook + `<PermissionGate>` component to hide UI.
   268→
   269→### 5.4 Multi-tenancy isolation
   270→Every business-scoped Prisma query filters by `businessId`. There is **no global admin override** that reads across tenants except via `/api/super-admin/**` routes (which require a separate super-admin Bearer token). The founder's `/admin` console reads across tenants using super-admin auth.

   274→## 6. AI Stack — The 9-Tier Defense
   275→
   276→Every AI route handler runs through this ordered gate before any LLM call:
   277→
   278→| # | Tier | Implementation | What it blocks |
   279→|---|---|---|---|
   280→| 1 | **Kill switch** | `ai-kill-switch.ts` | Per-pharmacy or platform-wide emergency off (4 dynamic triggers) |
   281→| 2 | **Subscription status** | `ai-rate-limit.ts` | `suspended` or `cancelled` business |
   282→| 3 | **Tier gate** | `feature-gate.ts` | Only `pro_ai` tier has `aiEnabled: true` |
   283→| 4 | **`aiEnabled` flag** | `Business.aiEnabled` | Manual founder override (separate from tier) |
   284→| 5 | **Circuit breaker** | `ai-circuit-breaker.ts` | Per-provider circuit (auto-recovers) |
   285→| 6 | **Burst** | `ai-rate-limit.ts` | 5 calls / 60s rolling window |
   286→| 7 | **Daily** | `ai-rate-limit.ts` | 50 calls / calendar day (overridable per-business) |
   287→| 8 | **Monthly** | `ai-rate-limit.ts` | 1000 calls / calendar month (overridable) |
   288→| 9 | **Token budget** | `ai-rate-limit.ts` | 500K tokens / month (overridable) |
   289→
   290→After the LLM call (success OR failure), the handler MUST call `logAIUsage(businessId, feature, tokensUsed, success, opts)` so the super-admin dashboard shows accurate spend.
   291→
   292→### 6.1 Kill-switch triggers (Phase 4)
   293→| Trigger | Default threshold | Auto-recover? |
   294→|---|---|---|
   295→| `per_pharmacy_monthly` | 200 BDT/month per pharmacy | No — manual reset |
   296→| `per_pharmacy_24h` | 50K tokens in 24h | No |
   297→| `platform_monthly` | 100K BDT/month platform-wide | No |
   298→| `zai_error_rate` | 10% errors in 1h | Yes — recovers when rate <1% for 30 min |
   299→
   300→When a trigger fires: a `KillSwitch` row is created (idempotent — won't duplicate), an email is sent to all `NotificationRecipient`s (up to 3), and the business's AI calls return a bilingual `kill_switch_open` fallback until reset.
   301→
   302→### 6.2 AI features (7 endpoints under `/api/businesses/[id]/ai/`)
   303→| Feature | Endpoint | Cached? | LLM? |
   304→|---|---|---|---|
   305→| Shelf scanner | `ai/shelf-scan` | No (image) | Yes (vision) |
   306→| Expiry optimizer | `ai/expiry-optimizer` | 24h | Yes |
   307→| Smart reorder | `ai/reorder` | No | **No** (deterministic; still logs usage) |
   308→| Smart forecast | `ai/forecast` | No | **No** (deterministic; still logs usage) |
   309→| AI insights | `ai/insights` | 24h | Yes |
   310→| Product assistant | `ai/product-assistant` | 7d for `generate_description` + `suggest_category` only | Yes |
   311→| AI chat | `ai/chat` | No | Yes |

   499→## 15. Deployment Workflow — Z.ai Sandbox ↔ GitHub ↔ WHM Production
   500→
   501→> **Full strategy documented in `DEPLOYMENT_WORKFLOW.md` — read it before your first push.**
   502→
   503→### The two environments
   504→| | Z.ai Sandbox (dev) | WHM Production |
   505→|---|---|---|
   506→| DB | Local PostgreSQL (system service) | Docker container + PgBouncer |
   507→| Runtime | Node.js (`npm run dev`, Turbopack) | Bun (`bun .next/standalone/server.js`) |
   508→| Proxy | None (`:3000` direct) | Caddy (`:81` → `:3000`) |
   509→| Secrets | `.env` (gitignored, local DB URL) | `.env` on server (gitignored, prod DB URL) |
   510→
   511→### The Golden Rule
   512→> **The repo is the source of truth for PRODUCTION. Z.ai uses gitignored overrides only.**
   513→>
   514→> If a change only makes sense in Z.ai → it goes in a gitignored file (`.env`, local scripts).
   515→> If a change makes sense in production → it goes in a committed file (`src/**`, `schema.prisma`, etc.).
   516→
   517→### Safe to push (environment-agnostic)
   518→`src/**`, `prisma/schema.prisma`, `prisma/migrations/**`, `prisma/seed.ts`, `public/**`, `package.json` (deps + lockfiles), `next.config.js`, `tsconfig.json`, `tailwind.config.ts`, `components.json`, `src/middleware.ts`, `download/**`, all `.md` docs.
   519→
   520→### Never push (gitignored, environment-specific)
   521→`.env`, `.env.local`, `.env.production`, `*.log`, `*.db`, `node_modules/`, `.next/`, `agent-ctx/`, `.z-ai-config`, `tool-results/`.
   522→
   523→### Modify with care (committed but environment-sensitive)
   524→`package.json` scripts (`dev`/`build`/`start`), `docker-compose.yml`, `Caddyfile`, `docker/pgbouncer/**`. Only modify these if the change benefits BOTH environments. For Z.ai-only scripts, ADD a new key (e.g., `dev:zai`) — don't modify existing.
   525→
   526→### Pre-push guardrail (MANDATORY before every push)
   527→```bash
   528→bash scripts/pre-push-check.sh
   529→```
   530→Verifies no `.env*` files, no `*.log`, no `*.db`, no `agent-ctx/` is staged. Exits non-zero if forbidden files found. Optional: install as a git pre-push hook (see `DEPLOYMENT_WORKFLOW.md` §5).
   531→
   532→### Standard workflow
   533→1. Make changes in Z.ai → test at `localhost:3000`
   534→2. `bash scripts/pre-push-check.sh` — must pass
   535→3. `git add` only the files you changed (be selective, avoid `git add .`)
   536→4. `git commit -m "feat(<scope>): <desc>"` → `git push origin main`
   537→5. On WHM: `git pull origin main` → `docker compose exec app npx prisma migrate deploy` (if schema changed) → `docker compose restart app`
   538→
   539→### Adding a new env var
   540→1. Add to `.env.example` (committed template, no real values)
   541→2. Add to local Z.ai `.env` (gitignored, real local value)
   542→3. Add to WHM server `.env` via SSH (real prod value)
   543→4. Document in §9 of this file
